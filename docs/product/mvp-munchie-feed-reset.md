# Munchie Feed 중심 2주 MVP 계약

## 제품 약속

사용자는 피드에서 가고 싶은 **식당 또는 코스**를 발견하고 저장하며, 다녀온 장소를 사진과 함께 다시 공유한다. 이 행동이 다음 추천을 개선하는 데이터로 연결된다.

핵심 루프는 하나다.

> 발견 → 상세 확인 → 식당/코스 저장 → 방문 → 게시 → 다음 추천 개선

## 구현 원칙

- 기존 Cloudflare 인증, D1, R2, 피드 API와 코스 데이터를 유지한다. 데이터베이스를 초기화하지 않는다.
- 기존 `courses` 모델을 재사용한다. 장소가 1개면 **식당 게시물**, 2개 이상이면 **코스 게시물**로 표현한다.
- 익명 사용자는 탐색할 수 있고, 저장·게시·반응은 Google 로그인 후 가능하다.
- 게시물 작성자와 상태는 서버 데이터를 원본으로 삼는다. 브라우저 캐시는 권한 또는 소유권 판단에 사용하지 않는다.
- 첫 2주에는 설명 가능한 규칙 기반 추천을 사용하고, 충분한 행동 데이터가 쌓이기 전에는 학습 완료를 주장하지 않는다.

## MVP 사용자 흐름

### 1. 첫 방문과 탐색

1. 앱을 열면 홈 소개 화면이 아니라 Munchie 피드가 보인다.
2. 사용자는 로그인 없이 게시물을 배치 단위로 탐색한다.
3. 카드에서 식당명, 대표 음식 사진, 위치/반경, 게시자, `식당` 또는 `코스` 유형을 즉시 구분한다.
4. 카드를 열면 게시물 상세와 연결된 식당 또는 순서가 있는 코스를 확인한다.

### 2. 저장과 방문 의도

1. 사용자가 식당 저장 또는 코스 저장을 누른다.
2. 비로그인 상태라면 Google 로그인 후 원래 화면으로 돌아온다.
3. 저장 목록에서 식당과 코스를 구분해 다시 볼 수 있다.
4. 지도 열기 또는 길찾기 버튼으로 실제 방문 행동을 연결한다.

### 3. 게시

1. 로그인한 사용자가 `+`를 누른다.
2. `식당 한 곳` 또는 `코스 만들기`를 선택한다.
3. 기존 식당을 검색·선택하고, 코스라면 2~5곳을 순서대로 추가한다.
4. 사진 1~5장과 짧은 한줄평을 입력한다.
5. 단순한 기본 레이아웃으로 미리보기 후 게시한다.
6. 게시 직후 본인 프로필과 공용 피드가 같은 서버 레코드를 보여준다.

### 4. 추천 데이터 선순환

피드 노출, 상세 열기, 저장, 좋아요, 지도 열기, 공유, 숨김, 게시를 서버 이벤트로 기록한다. 추천은 다음 요소를 사용한다.

- 사용자가 저장하거나 긍정 반응한 카테고리·식당
- 현재 선택한 지역 또는 반경
- 최신성 및 게시물 품질
- 같은 식당·작성자·카테고리의 연속 노출 제한
- 일부 새로운 카테고리를 섞는 탐색 슬롯

## 화면 구조

하단 내비게이션은 MVP에서 세 개와 작성 버튼만 유지한다.

- **발견**: 개인화된 Munchie 피드
- **저장**: 저장한 식당과 코스
- **내 정보**: 내 게시물과 최소 프로필 설정
- **+ 게시**: 식당 또는 코스 게시 시작

상세 화면은 게시물, 식당/코스 정보, 저장, 지도 열기, 공유에 집중한다.

## 기존 구현 재사용

- Google OAuth와 서버 세션
- `/api/feed` 배치 조회 및 개인화 랭킹
- `courses`, `course_items`, `course_media`, `saved_courses`, `rec_events`
- R2 사진 저장·검증
- Munchie 피드 카드와 상세 페이지
- 저장 목록과 지도 연결
- 프로필 피드의 서버 원본 조회
- 작성자/관리자 삭제 권한 및 관리자 운영 화면

## 2주 MVP에서 제외

- Lunchie 실시간 그룹 투표, 초대, 로비, 다인 알고리즘
- Lunchmate 성장·코스튬·게임화
- 자유 배치 스크랩북 편집과 다수 템플릿 제작
- Tour Mode와 별도 탐색 모드
- 팔로우 네트워크 고도화와 복잡한 알림
- ML 모델 학습 자동화 및 과도한 페르소나 표현

기존 코드는 즉시 삭제하지 않고 라우팅과 내비게이션에서 숨긴다. 운영 안정화 후 데이터·사용 여부를 확인해 별도 제거한다.

## 데이터 계약

모든 공개 게시물은 다음을 만족해야 한다.

- 인증된 `author_id`
- 고유한 `course_id`
- 1개 이상의 유효한 식당 연결
- 1개 이상의 존재하는 R2 이미지
- 게시 유형: 식당(장소 1개) 또는 코스(장소 2~5개)
- 생성 시각과 공개 상태

클라이언트가 보낸 작성자 ID는 신뢰하지 않으며 서버 세션에서 결정한다. 삭제 시 게시물과 연결된 코스·미디어·반응 데이터를 서버에서 일관되게 처리한다.

## 성공 조건

- 새 사용자가 설명 없이 피드를 탐색하고 식당 또는 코스를 구분할 수 있다.
- 비로그인 탐색과 로그인 후 원래 행동 복귀가 작동한다.
- 식당 한 곳 또는 2~5곳 코스를 2분 안에 게시할 수 있다.
- 게시물이 공용 피드와 작성자 프로필에서 동일하게 보인다.
- 저장한 식당/코스가 새로고침과 다른 기기에서도 유지된다.
- 피드는 한 번에 전부가 아니라 배치 단위로 로드된다.
- 끊어진 이미지, 잘못된 작성자, 삭제 게시물 재등장이 없다.
- 핵심 이벤트가 관리자 대시보드에서 집계된다.

## 2주 전달 순서

### 1주차

1. 정보 구조와 라우팅을 Munchie 피드 중심으로 축소
2. 피드 카드와 상세에서 식당/코스 유형 및 저장 CTA 정리
3. 로그인 게이트와 원래 행동 복귀 검증
4. 게시 플로우를 장소 선택 → 사진/한줄평 → 게시로 단순화

### 2주차

1. 저장 목록을 식당/코스 기준으로 정리
2. 핵심 행동 이벤트와 추천 다양성 규칙 연결
3. 이미지·소유권·페이지네이션·삭제 E2E 보강
4. 모바일 실제 기기 검증, 운영 데이터 마이그레이션 확인, 프로덕션 배포

## 브랜치 전달 방식

`codex/mvp-munchie-feed-reset`을 2주 MVP 통합 기준으로 사용한다. 실제 작업은 사용자 흐름 단위의 작은 커밋으로 나누며, 각 커밋은 관련 테스트를 포함한다. 다른 팀원의 진행 중 기능은 자동으로 가져오지 않고 MVP 계약에 필요한 경우에만 검토 후 통합한다.
