# 런치 엔진 탐색·활용 정책 설계 — 유저 플로우에서 출발

- 날짜: 2026-07-26
- 상태: **설계(로직) · 코드 미착수 · 승인 대기**
- 배경: 감사에서 P0·P1을 고쳤으나, **탐색→활용 스케줄이 설계된 적이 없다.**
  `MIN_TASTE=5` 게이트가 Thompson Sampling을 무력화하고 있음을 발견.

---

## 0. 큰 틀 — 엔진은 "유저와의 대화"다

이 앱의 엔진은 추천 목록을 뱉는 배치 시스템이 아니다. **유저가 스와이프할 때마다
질문하고 답을 듣는 루프**다. 그래서 설계의 기준은 "정확도"가 아니라
**"각 화면이 얼마나 좋은 질문인가"**여야 한다.

```
        ┌──────────── 이 루프가 엔진의 전부 ────────────┐
        │                                              │
  질문(슬레이트 노출) → 답(스와이프/듀얼/우승) → 갱신(θ 사후분포)
        │                                              │
        └──── 사후분포가 좁아질수록 질문이 '맞춤'으로 ──┘
```

**핵심 원리(밴딧/RL)**: 탐색이 곧 데이터 생성이다. 별도의 "데이터 수집 단계"가 없다.
사후분포에서 θ를 샘플(Thompson)하면 — 데이터가 없을 땐 분산이 커서 샘플이 크게 흔들리고
(= 넓은 탐색), 쌓일수록 좁아져 저절로 활용으로 넘어간다. **스케줄을 손으로 짤 필요가 없다.**

> 지금 코드는 이 원리를 `MIN_TASTE=5` 게이트로 막고 있다. 이 문서가 고치려는 것이 그것이다.

## 1. 유저 플로우와 각 단계의 정보량

### 1-1. 솔로 첫 세션 (완전 신규 유저)

| 단계 | 화면 | 유저 행동 | 엔진이 얻는 정보 |
|---|---|---|---|
| 설정 | 필터·인텐트 | 인텐트·동행·반경 | **맥락**(하드 필터) — 학습 아님 |
| 예선 | 카드 7장 | LIKE / NOPE ×7 | **pointwise 7건** ← 정보의 대부분 |
| 결승 | 듀얼 A vs B | 하나 고르기 | **pairwise 1건** (가장 깨끗한 선호) |
| 〃 | 〃 | 둘 다 별로 | 음성 2건 + "top-2가 틀렸다" |
| 우승 | 우승화면 | 확정 | 강한 긍정 1건 (w=2) |
| 회고 | 홈 SURVEY | 👍😐👎 | **만족 정답** (지연 라벨) |

**한 세션 ≈ 9~10 관측.** 즉 **첫 세션 한 번이면 `MIN_TASTE=5`를 넘긴다.**
→ 게이트가 실제로 영향을 주는 구간은 **생애 첫 7장**뿐이다.
→ 그런데 그 7장이 **첫인상이자, 유저에 대해 아무것도 모를 때의 유일한 질문 기회**다.
   여기가 설계의 급소다.

### 1-2. 그 이후

| 세션 | 관측 누적 | 사후분포 상태 | 엔진 행동(자동) |
|---|---|---|---|
| 1 | 0 → 10 | 사전 → 느슨 | 넓은 탐색 |
| 2~3 | ~30 | 축 몇 개 수렴 | 탐색·활용 혼재 |
| 5+ | ~50 | 좁음 | 활용 우세, 불확실한 축만 탐색 |
| 재진입 | — | chain 켜짐 | 다음-스톱 제안 |

**설계 결론**: 스케줄을 만들 필요가 없다. **게이트만 없애면 위 표가 저절로 나온다.**

## 2. 핵심 설계 — 3단계 (경계는 자동)

### Stage 0 · 생애 첫 슬레이트 (n = 0) — **정보 최대화**
유저에 대해 아는 게 없다. 이때 "가장 좋아 보이는 7곳"(=전역 평판 상위)을 주는 건
**최악의 질문**이다 — 서로 비슷해서 어떤 답이 와도 배우는 게 적고, 모든 신규 유저가 같은 화면을 본다.

> **원칙: 첫 슬레이트는 보상이 아니라 정보를 최대화한다.**

베이지안 선형모델에서 정보량은 사후 정밀도 `A = λI + Σ x xᵀ` 의 `log det A` 증가분이다.
→ **피처 공간에서 서로 멀리 떨어진 7장**을 고르면 det가 커진다(D-최적 설계의 탐욕 근사).

구현 방침: 하드 필터(인텐트·식이·거리) 통과 후,
`평판 사전확률 × 피처 다양성`으로 탐욕 선택 — 이미 고른 것들과 피처 거리가 먼 후보를 우선.
(MMR과 같은 형태. 품질을 완전히 버리지 않도록 사전확률을 곱한다.)

### Stage 1 · 학습 중 (n ≥ 1) — **Thompson이 알아서**
`sampleTheta(t)`를 **게이트 없이** 항상 호출한다. n이 작으면 사후분포가 넓어
샘플이 흔들리고 → 자연스러운 탐색. n이 커지면 좁아져 → 자동 활용.
**단절(계단식 점프)이 사라진다.**

### Stage 2 · 수렴 후 — 별도 로직 없음
Stage 1과 같은 코드다. 사후분포가 좁아졌을 뿐이다.

## 3. 결정해야 할 파라미터 (근거와 함께)

| 파라미터 | 현재 | 제안 | 근거 |
|---|---|---|---|
| `MIN_TASTE` | 5 (게이트) | **제거** | 베이지안 모델엔 불필요. 게이트가 Stage 0/1 단절을 만듦 |
| `PRIOR` (A₀=λI) | 1.0 | **시뮬로 결정** | 작을수록 첫 스와이프에 과반응, 클수록 학습 느림 |
| `eps` (ε-혼합) | 0.05 | **Stage별 차등** | Thompson이 취향 축을 탐색하므로 ε은 *비학습 축*(평판·맥락) 보험용으로만 |
| `tau` (softmax) | 0.15 | **시뮬로 결정** | 점수 폭이 P1으로 0.482까지 커져 τ 재조정 필요 |

**ε과 Thompson의 역할 분담** — 중복이 아니다:
- **Thompson**: 취향 θ의 불확실성을 탐색 (학습되는 축)
- **ε**: 평판·맥락처럼 **학습되지 않는 축**의 편향에 대한 보험, 그리고 propensity가
  0에 붙지 않게 하는 안전장치(IPS 분모 보호)
→ ε을 0으로 두면 off-policy 평가가 깨진다. **작게 유지**하되 Thompson과 별개 목적으로 문서화.

## 4. 그룹은 어떻게 (지금 설계 공백)

현재: 멤버 중 `n ≥ MIN_TASTE`인 사람만 `memberThetas`에 넣고, **콜드 멤버는 통째로 제외**된다.
→ 5명 중 1명만 학습돼 있으면 **그 1명의 취향으로 그룹 전체를 결정**한다. least-misery 취지에 반한다.

**설계**: 콜드 멤버도 **사전분포에서 샘플**해 참여시킨다(θ ~ N(0, A₀⁻¹)).
- 콜드 멤버의 샘플은 중립 근처에서 크게 흔들림 → least-misery의 min 연산에서
  "이 사람은 어떨지 모른다"가 **불확실성으로 정직하게 반영**된다.
- 전원 콜드면 지금처럼 `tasteFit = null`(평판·맥락만).

## 5. 검증 계획 — 시뮬레이션으로 근거 만들기

파라미터를 손으로 정하지 않는다. **가상 유저 실험**으로 정한다.

```
가상 유저 U를 θ* (참 취향)으로 정의
  → 엔진이 슬레이트 제시 → U가 sigmoid(θ*·x) 확률로 LIKE
  → 엔진 학습 → 반복
측정:
  ① 학습곡선  — 스와이프 수 대비 ‖μ̂ − θ*‖ (얼마나 빨리 취향을 잡나)
  ② 후회(regret) — 매 세션 선택한 곳의 참 효용 vs 최적 대비
  ③ 첫 세션 만족도 — 생애 첫 7장의 평균 sigmoid(θ*·x)  ← Stage 0 설계의 직접 지표
  ④ 커버리지 — 카탈로그 탐색 폭
비교 정책:
  A. 현행(MIN_TASTE 게이트)   B. 게이트 제거만
  C. 게이트 제거 + Stage 0 다양성   D. 랜덤 베이스라인
```

**성공 기준**: C가 A보다 ①이 빠르고 ③이 나쁘지 않아야 한다.
(③이 크게 나빠지면 "정보 최대화"가 첫인상을 해치는 것이므로 다양성 가중을 낮춘다.)

시뮬레이터는 감사 때 쓴 것을 확장해 만든다 — **배포 전에도 설계를 검증할 수 있다.**
이것이 "데이터가 없어서 못 정한다"에 대한 답이다.

## 6. 이 설계가 답하는 것 / 답하지 않는 것

**답한다**
- 신규 유저 첫 화면에 무엇을 보여줄 것인가 (정보 최대화)
- 언제 개인화로 넘어가는가 (자동 — 사후분포가 결정)
- 그룹에 콜드 멤버가 섞이면 (사전분포 샘플로 참여)
- 파라미터를 어떻게 정하는가 (시뮬레이션)

**답하지 않는다 (별건)**
- `contextWeights` 값의 근거 — 현재 손으로 정한 값. 맥락은 θ에 들어가지 않아
  **밴딧 루프 밖**이다. 맥락까지 학습하려면 피처를 `x ⊗ context`로 확장해야 하는데,
  차원이 곱으로 늘어 데이터 요구량이 급증한다 → **v2 과제로 분리**.
- 오프라인 정밀 학습(Python) — 온라인 루프와 독립.

## 7. 작업 순서 (승인 후)

1. **시뮬레이터** 작성 (가상 유저 + 학습곡선/후회 측정) — 코드지만 엔진 변경 없음
2. 정책 A/B/C/D 비교 → `PRIOR`·`eps`·`tau` 결정 (근거 기록)
3. `MIN_TASTE` 제거 + 그룹 콜드 멤버 참여
4. Stage 0 다양성 슬레이트
5. 회귀 테스트 + 학습곡선 기준선 고정

> 2번이 끝나기 전에는 3~4를 건드리지 않는다. 파라미터를 추측으로 정하면
> P1에서 `contextWeights`를 손으로 정한 것과 같은 실수를 반복하게 된다.
