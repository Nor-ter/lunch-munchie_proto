# 자율 이슈 해결 시스템 설계

> 목적: `google-maps-integration-work-log.md`에서 사람(Inseong)이 직접 판단·중재하며 풀었던 디버깅 과정을, Claude Code가 **최소 개입으로 스스로 반복**할 수 있도록 워크플로우·에이전트·안전 게이트로 구조화한다.
> 스택: Supabase(Edge Functions + Postgres + Auth) · Expo/React Native · Google Maps Platform
> 자율성 수준: **안전 게이트가 있는 자율** — 코드/디버깅은 자율, 파괴적·비용·보안 작업만 사람 승인.

---

## 0. 이 설계가 나온 근거 (work-log에서 뽑은 5개 교훈)

작업 로그 §6의 교훈을 그대로 시스템 규칙으로 번역했다.

| 교훈 (로그 §6) | 시스템 규칙으로 번역 |
|---|---|
| ① 표면 원인 ≠ 실제 원인. "저장 실패" 뒤에 익명로그인 비활성화 + 화면 미구현이 순차로 숨어 있었다 | **계층적 근본원인 분석(RCA) 루프** — 하나 고쳐도 증상이 남으면 "다음 층"을 자동으로 판다 (§3) |
| ② 로그를 어디서 볼지 아는 게 속도를 좌우 | **로그 소스 사다리** 를 고정 순서로 명문화 (§4) |
| ③ 화면 없어도 백엔드 검증 가능 (SQL insert + 딥링크) | **화면-우회 검증 레시피** 를 재사용 도구로 등록 (§5) |
| ④ 보안은 "됐다"고 넘기지 말고 재확인 | **보안 점검을 종료 게이트로 강제** (§6) |
| ⑤ 외부 서비스 장애를 디버깅 판단에 넣어라 | **외부 장애 선제 체크** 를 RCA 진입 조건에 포함 (§4.3) |

핵심 철학 한 줄: **"증상 하나 = 원인 하나"라고 가정하지 않는다. 고치고 → 재현하고 → 남은 증상이 있으면 로그 사다리를 한 칸 더 내려간다."**

│   4) VERIFY   ─ 화면-우회 레시피로 백엔드 로직 독립 검증        │
│   5) GATE     ─ 보안·회귀 점검 후에만 "완료" 선언              │

 │debugger    │  │verifier    │  │auditor     │
 │(로그 파기) │  │(우회 검증) │  │(종료 게이트)│
 └────────────┘  └────────────┘  └────────────┘
        │               │               │
        ▼               ▼               ▼
 ┌──────────────────────────────────────────────────────────────┐
 │  SAFETY GATE (PreToolUse 훅)                                   │
 │  파괴적/비용/보안 명령을 가로채 사람 승인 요청                 │

메인 세션이 **오케스트레이터**, 반복적·독립적 조사는 **서브에이전트**로 분리한다. 서브에이전트는 자기 컨텍스트에서 로그를 잔뜩 읽어도 메인 컨텍스트를 오염시키지 않고 결론만 반환한다(로그 §6-②의 "로그 위치 찾기"를 병렬화).

## 2. 6단계 루프 상세

### 2.1 TRIAGE (증상 분류)
- 이슈를 한 문장 증상으로 정규화한다. 예: "순서 변경 후 저장 실패 토스트".
- **외부 장애 선제 체크**(로그 §6-⑤): 조사 시작 전에 `status.supabase.com`, Google Cloud status를 먼저 확인. 장애 중이면 RCA를 멈추고 무관한 안전 작업(gitignore, 키 정리 등)으로 전환하거나 사람에게 알린다.
- 증상 유형 태깅: `auth` / `rls` / `edge-function` / `client-key` / `build` / `data-state`. 태그에 따라 로그 사다리 진입점이 달라진다(§4).

### 2.2 RCA LOOP (근본원인 파기)
로그 §6-①의 핵심. **한 번에 한 층만 고치고 다시 재현한다.** 자세한 규칙은 §3.

### 2.3 FIX (최소 변경)
- 가장 작은 변경으로 한 가지 원인만 해결. 여러 원인이 의심돼도 한 번에 하나씩.
- 변경이 **안전 게이트 목록**(§6.1)에 걸리면 실행 전 정지하고 승인 요청.

### 2.4 VERIFY (화면-우회 검증)
로그 §6-③. UI가 없어도 SQL 직접 insert + Expo 딥링크로 대상 화면·데이터를 만들어 백엔드 로직만 독립 검증. 레시피는 §5.

### 2.5 GATE (종료 게이트)
로그 §6-④. 기능이 됐다고 끝이 아니다. `security-auditor`가 통과시켜야 "완료" 선언.

### 2.6 LOG (회고 append)
매 사이클 종료 시 work-log 형식(증상→원인층들→해결→남은 TODO)으로 append. 다음 세션의 학습 자료이자 감사 로그.

## 3. 계층적 RCA 루프 (교훈 ① 구현)

```
        ┌─────────────────────────────┐
        │ 증상 재현 (reproduce)        │◄─────────────┐
        └──────────────┬──────────────┘              │
                       ▼                             │
        ┌─────────────────────────────┐              │
        │ 로그 사다리 한 칸 조회(§4)   │              │
        └──────────────┬──────────────┘              │
                       ▼                             │
        ┌─────────────────────────────┐              │
        │ 가설 1개 세우고 최소 수정    │              │
        └──────────────┬──────────────┘              │
                       ▼                             │
        ┌─────────────────────────────┐    증상 남음  │
        │ 다시 재현                    ├──────────────┘
        └──────────────┬──────────────┘
                       │ 증상 사라짐
                       ▼
                    VERIFY(§5)
```

멈춤 규칙(무한루프 방지):
- 같은 층에서 **가설 3회 실패** 시 → 사람에게 요약 보고(증상, 시도한 3개, 각각의 로그 근거) 후 대기.
- **로그 사다리 최하단까지 갔는데도** 원인 불명 → 사람 호출.
- 수정이 안전 게이트에 걸림 → 사람 승인 대기(자율 종료 아님, 일시 정지).

로그에서 실제로 이 루프가 돌았던 예: 저장실패 → (층1) Metro 로그: 익명로그인 비활성화 → 켜고 재현 → 여전히 실패 → (층2) Postgres 로그: `42501 RLS 위반` → courses 조회로 "새 코스가 만들어진 적 없음(seed 코스 편집 중)" 발견 → 진짜 원인은 화면 미구현.

## 4. 로그 소스 사다리 (교훈 ② 구현)

증상 태그별 **고정 조회 순서**. 위에서부터 내려가며, 각 칸에서 "이 층이 말이 되는가"를 판단.

### 4.1 저장/쓰기 실패 계열 (`auth`/`rls`/`data-state`)
1. **Metro / 앱 콘솔 로그** — 클라이언트에서 실제로 뭘 보냈나, 인증 상태는? (예: `익명 로그인 실패: Anonymous sign-ins are disabled`)
2. **Supabase Postgres Logs** — DB가 거부한 에러 코드. `42501`=RLS 위반, NOT NULL 위반 등.
3. **데이터 상태 직접 조회(SQL Editor)** — "그 행이 실제로 존재/소유가 맞나?" 로그 §4.2에서 courses가 seed뿐임을 발견한 결정적 단계.
4. **Supabase API Logs / Edge Function Logs** — 요청 body·응답까지.

### 4.2 검색/경로 계열 (`edge-function`/`client-key`)
1. **Edge Function Logs** — 프록시가 Google에 뭘 보내고 뭘 받았나.
2. **Google Cloud API 대시보드** — 키 제한/쿼터/거부.
3. 클라이언트 키 vs 서버 키 경로 구분(로그 §4.3 교훈): add/검색은 **서버 키 기반 Edge Function 경로** → 클라이언트 키 교체와 무관. 원인을 엉뚱한 곳에서 찾지 않도록 경로부터 확정.

### 4.3 외부 장애 게이트
어느 층에서든 "로그 자체가 안 보임 / 5xx / 타임아웃"이면 **내 설정 탓으로 오인하지 말고**(로그 §6-⑤) 먼저 status 페이지 확인. 장애면 디버깅 중단 → 안전 작업으로 전환 or 사람 통지.

### 4.4 빌드 계열 (`build`)
1. `xcodebuild` / prebuild 출력 전문.
2. `xcodebuild -showdestinations`로 시뮬레이터 런타임 매칭 확인(로그 §3: Xcode↔iOS 런타임 버전 호환이 exit 70의 진짜 원인이었음).
3. 캐시 삭제(`.expo`, DerivedData)는 **가설이지 만능 아님** — 로그에서 캐시 삭제가 헛수고였던 사례 반영, 우선순위 낮게.

## 5. 화면-우회 검증 레시피 (교훈 ③ 구현)

UI 화면이 미구현이어도 백엔드 로직을 독립 검증하는 재사용 절차. `backend-verifier` 에이전트가 수행.

1. **현재 세션의 실제 uid 확보**: `auth.users`에서 현재 익명 세션 uid 조회. (author_id 불일치가 재발하지 않도록 웹 프로토타입 우회는 쓰지 않음 — 로그 §4.2의 판단.)
2. **테스트 데이터 직접 insert**: 그 uid를 `author_id`로 하는 `courses` 행 insert. NOT NULL 컬럼(`total_distance` 등) 빠짐없이 채운다(로그의 실패 경험 반영).
3. **참조 데이터 연결**: 기존 `restaurants` 행을 참조하는 `course_items` insert.
4. **딥링크로 대상 화면 직접 진입**: `app.config.ts`의 `scheme`(`lunchie-munchie`) 확인 후
   `xcrun simctl openurl booted "lunchie-munchie://course/<id>/edit"`.
5. **검증 후 정리**: 테스트 행은 태그(예: `source='test'`)로 만들어 두고 사이클 끝에 정리.

이 레시피 덕분에 "전체 화면을 먼저 다 구현할 필요 없이" 저장 로직만 검증 가능(로그 §6-③).

## 6. 안전 게이트 (교훈 ④ + 자율성 경계)

### 6.1 사람 승인이 필요한 작업 (PreToolUse 훅이 차단)
- **파괴적**: `supabase db reset`, `rm -rf`, `git push --force`, 마이그레이션 되돌리기, 테이블 DROP.
- **비용/배포**: `supabase functions deploy`, `supabase secrets set`, 프로덕션 대상 curl 대량 실행.
- **보안**: `gcloud ... keys delete/create`, 키 regenerate, `.env` 값 쓰기.
자율로 허용: 읽기(로그·DB 조회), 로컬 테스트, 코드 편집, 로컬 SQL insert(테스트 데이터), 로컬 `supabase functions serve`.

### 6.2 종료 보안 게이트 (`security-auditor`)
"완료" 선언 전에 반드시 통과해야 하는 체크리스트(로그 §5에서 나온 실제 항목들):
- Google 키가 **클라이언트/서버 분리**되어 있고 각각 API restriction이 걸렸는가.
- 무제한(Application restriction=None, 전체 API 허용) 방치 키가 없는가 — 로그 §5.1에서 중복 무제한 키 2개가 발견된 사례.
- 클라이언트 빌드에 서버 키가 박혀 노출되지 않았는가(`EXPO_PUBLIC_*` grep).
- `.env`, `env.enc` 등 민감 파일이 `.gitignore`에 있는가(로그 §5.3 미완료 TODO).
- 미완료 보안 TODO(Android SHA-1 제한 등)를 명시적으로 리포트.

이 게이트는 "기능 됨 = 끝"을 막는다. 로그 §6-④ 그대로.

## 7. 파일 구성 (이 설계와 함께 제공)

```
.claude/
├── CLAUDE.md                     # 프로젝트 규칙 + 6단계 루프 + 게이트(항상 로드)
├── settings.json                 # PreToolUse 안전 게이트 훅 등록
├── hooks/
│   └── safety-gate.sh            # 파괴적/비용/보안 명령 차단 스크립트
├── agents/
│   ├── issue-debugger.md         # 로그 사다리 따라 RCA (§3,§4)
│   ├── backend-verifier.md       # 화면-우회 검증 (§5)
│   └── security-auditor.md       # 종료 보안 게이트 (§6.2)
└── commands/
    └── resolve-issue.md          # 6단계 루프 진입 슬래시 커맨드
```

각 파일은 이 문서의 해당 절을 실행 가능한 지시로 옮긴 것이다.

## 8. 사용 흐름 (사람 개입 최소 시나리오)

1. 사람: `/resolve-issue 순서 변경 후 저장이 실패함` 한 줄만 입력.
2. Claude Code: TRIAGE(외부 장애 체크) → RCA 루프(Metro→Postgres→데이터상태) → 원인 발견 → 최소 수정.
3. 수정이 `supabase functions deploy` 같은 게이트 항목이면 → 여기서만 사람에게 "배포해도 될까요?" 승인 요청.
4. VERIFY(SQL insert + 딥링크로 독립 검증) → GATE(보안 점검) → work-log append → 완료 보고.
5. 사람은 (2)(4)는 안 보고 있어도 되고, (3) 승인과 (5) 결과만 확인.

이렇게 하면 로그에서 사람이 일일이 판단했던 "로그 어디 보지?/이거 진짜 원인 맞나?/보안 됐나?"를 시스템이 대신 돌고, 사람은 **파괴적·비용·보안 결정에만** 개입한다.
